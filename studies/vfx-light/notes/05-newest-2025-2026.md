# 05 — Newest developments (mid-2025 → 2026-11-09): 2D / pixel-art light & shadow, Godot, web

Researcher angle: what is NEW and relevant to Kingsfoil (Godot 4, web-first => Compatibility/WebGL2, top-down pixel art).
Status labels: **[SHIPPED]** = in a stable release/product; **[EXPERIMENTAL]** = flagged experimental, research or demo; **[DATE?]** = date not verified.

---

## Q1. Godot 4.4 → 4.7: what changed for 2D lighting/shadows?

### Takeaway
- **Nothing in 4.4–4.7 changed the core 2D light model** (PointLight2D / DirectionalLight2D / LightOccluder2D / CanvasModulate). Release highlights for 4.5, 4.6 and 4.7 list no 2D light or 2D shadow features. The changes that matter for us are *around* lighting: **DrawableTexture2D (4.7)** is a cheap GPU-drawn light-map/fog-of-war canvas; 2D batching now on all renderers (4.4); CanvasItem **instance uniforms** (4.4) let each torch/lamp sprite have its own flicker phase/colour without breaking batching; **HDR output (4.7)**; glow blended before tonemapping (4.6).
- For web we stay on Compatibility. The docs still say additive sprites are "much faster" than real 2D lights. That fits our "cheap tricks" direction.

### Cited findings
- **Release dates:** 4.4 stable 2025-03 (release page shows "26 March 2025" for its last maintenance entry; https://godotengine.org/releases/4.4/). 4.5 published 2025-09-16 (CG Channel, https://www.cgchannel.com/?p=170196). 4.6 2026-01-27 (CG Channel, https://www.cgchannel.com/?p=173665). 4.7 released mid-June 2026: cinevva says 2026-06-19 (https://app.cinevva.com/news/2026-06-19-godot-4-7-released), CG Channel post 2026-06-23 (https://www.cgchannel.com/?p=176830). Exact 4.7 day not checked on godotengine.org. **[DATE? ±days]**
- **4.4, 2D batching:** "Previously, this optimization was only available in the Compatibility renderer." 4.4 brought it to the other backends (https://godotengine.org/releases/4.4/).
- **4.4, CanvasItem instance uniforms:** "more performant than having to juggle materials, and does not break batching" (https://godotengine.org/releases/4.4/). → one shared torch-flicker material, with a per-instance `phase` and `tint`.
- **4.5:** the 2D items are chunked TileMapLayer physics. The web item is **WASM SIMD**, described as smoother web games "without having to do anything" (https://godotengine.org/releases/4.5/). There is no 2D-light item.
- **4.6:** rotatable scene tiles. The page's own example is "a glowing lamp, or a torch" as scene tiles, rotated in 90° steps. Glow is now "blended before tonemapping", with Screen as the default mode. With HDR 2D on, colour precision is kept through the pipeline (https://godotengine.org/releases/4.6/).
- **4.7 DrawableTexture2D [SHIPPED but methods marked EXPERIMENTAL]:** "a simple API layer that abstracts away all the technical noise". It replaces Viewport/RenderingDevice workarounds. PR #105701 by Colin O'Rourke (https://godotengine.org/releases/4.7/).
  - API (https://docs.godotengine.org/en/4.7/classes/class_drawabletexture2d.html): `setup(w,h,format,color=white,use_mipmaps=false)`, `blit_rect(rect:Rect2i, source:Texture2D, modulate, mipmap, material)`, `blit_rect_multi(...)` (up to 4 sources and 3 extra targets), `generate_mipmaps()`. Formats: `RGBA8`, `RGBA8_SRGB`, `RGBAH` (GL_RGBA16F) and `RGBAF` (GL_RGBA32F). `blit_rect`, `blit_rect_multi` and `setup` are tagged "Experimental: This method may be changed or removed".
  - Blending is set by a new `shader_type texture_blit` with `blend_mix`/`blend_add`/`blend_sub`/`blend_mul`/`blend_disabled`. Premultiplied alpha is not supported. `BlitMaterial.blend_mode` can override per call (https://docs.godotengine.org/en/4.7/tutorials/rendering/drawable_textures.html).
  - The class docs describe the formats in OpenGL terms ("OpenGL texture format…"), which suggests a GLES3/Compatibility path exists. **Not verified.** The GitHub PR page was blocked in this session.
- **4.7 HDR output** works on Windows, macOS, iOS, visionOS and Linux (Wayland) for 2D and 3D. Web is not listed (https://godotengine.org/releases/4.7/).
- **4.7 also adds:** `GradientTexture2D` FILL_CONIC (CSS-style conic gradients, useful for cone/flashlight masks), `AtlasTexture` in `TextureRect`, and a 2D Scene Paint mode (`B`) for scattering props such as torches (https://godotengine.org/releases/4.7/).
- **2D light docs (4.6 manual), current state:** CanvasModulate darkens the scene. Light blend modes are Add (default), Subtract and Mix. Shadow filters are None/PCF5/PCF13; "PCF13 is even softer, but is the most demanding". Too high a Filter Smooth gives banding/streaking. `LightOccluder2D` "SDF Collision" is on by default and "has no performance cost" unless shaders read the SDF. Both light types support normal and specular maps through CanvasTexture. Section heading: "Using additive sprites as a faster alternative to 2D lights". Additive sprites "cannot cast shadows" and ignore normal maps (https://docs.godotengine.org/en/4.6/tutorials/2d/2d_lights_and_shadows.html).
- **Project settings (4.7):** `rendering/2d/shadow_atlas/size = 2048`. `rendering/2d/sdf/scale` defaults to 50% (half resolution per axis, so 25% of the pixels). `rendering/2d/sdf/oversize` defaults to 100%, with higher values covering off-screen occluders. `rendering/viewport/hdr_2d = false`; when enabled it uses an RGBA16 framebuffer and linear blending, which allows "2D glow". 3D-only GL limits: `max_lights_per_object = 8`, `max_renderable_lights = 32` (https://docs.godotengine.org/en/4.7/classes/class_projectsettings.html).
- **Third-party claim:** the Lit addon page says built-in Godot 2D lights have a "~15-lights-per-object cap" (https://store.godotengine.org/asset/fading-lantern-games/lit-2d-lighting-engine/). This is a vendor statement. I did not find it in the official docs.

### Inferences
- **DrawableTexture2D as a light accumulation buffer:** keep a low-res light map (e.g. 1 texel per tile, or 1/4-res screen). Each frame, `blit_rect` soft light stamps into it with `blend_add`. Fog-of-war "explored" memory can use `blend_mix`, and darkness can use `blend_mul`. Then multiply the map over the world in one canvas shader. This replaces the old "SubViewport of additive light sprites" trick. The API is experimental, so wrap it behind our own helper.
- CanvasItem instance uniforms plus additive light sprites is probably the cheapest "many torches" path on WebGL2: one material, one batch, per-torch flicker.
- HDR 2D on web: untested here, and the RGBA16F render target may cost a lot on low-end mobile/WebGL. For a palette-limited look we don't need it.

### Gaps
- No official statement of the Compatibility-renderer 2D light limits (lights per item, shadow support differences) in 4.5–4.7. Benchmark this ourselves.
- DrawableTexture2D support on Compatibility/web is not confirmed.
- The 4.7 release-page fetch covered only ~93% of the page, so a minor 2D item may be missing.

## Q2. Radiance cascades (RC) & 2D global illumination

### Takeaway
- RC is the notable new **2D GI** technique. It is noiseless and its cost is fixed for a given resolution. Good demos run in **WebGL fragment shaders** (three.js), so it is technically web-viable. The cost is a full screen of multi-pass work: a jump-flood SDF (log2(N) passes) plus one pass per cascade (about 4–6). Vanilla RC still has **ringing artifacts**, and fixes can roughly double frame time.
- **Holographic Radiance Cascades** (May 2025) is the newest refinement: 1.85 ms at 512² and 7.67 ms at 1024² on an RTX 3080 *laptop* GPU. Mobile/iGPU WebGL would be much slower. **[EXPERIMENTAL/research]**
- For low-res pixel art (e.g. 320×180 or a 1-texel-per-tile light map), RC at low res is plausible on desktop browsers. It is overkill for a Tibia-like game: GI bounce is not part of that look. **Verdict: optional showcase for "magic" scenes, not a baseline.**

### Cited findings
- **Holographic RC:** Rouli Freeman, Alexander Sannikov, Adrian Margel, arXiv 2505.02041, submitted 2025-05-04. Claims results "visually indistinguishable from the 2D reference solution at realtime framerates", with cost constant for a given scene size. Timings: 1.85 ms at 512×512 and 7.67 ms at 1024×1024 on an RTX 3080 Laptop (https://arxiv.org/abs/2505.02041).
- **jason.today, "Building Real-Time Global Illumination"** (Part 1, 2024-07-27, https://jason.today/gi) and **"Radiance Cascades"** (Part 2, datePublished 2024-08-31, https://jason.today/rc). These are 2024 posts but still the main open tutorials. Interactive three.js/WebGL.
  - Naive GI: 1024² × 512 rays ≈ 500M rays/frame, so "roughly 100x" too slow for 16 ms (https://jason.today/rc).
  - Penumbra hypothesis: far light needs more angular resolution and less spatial resolution. Cascades start "256 rays and 1/16th resolution" and go down to base rays at full res. The base ray count is 4 or 16, so the ray count is 4 near and 16 far (or 16 and 256) (https://jason.today/rc).
  - Performance knobs in the demo: "Pixels Between Base Probes" = 2, `rcScale` 2 (renders at 0.5 res), `pixelRatio`, and "Calculate over 2 frames" (https://jason.today/rc).
  - Ringing: "still an active area of research", and fixes can mean "doubling the frame time". Work in linear space (pow 2.2) because WebGL is sRGB (https://jason.today/rc).
  - JFA uses log(N) passes of the largest dimension (https://jason.today/gi).
- **Other open implementations:**
  - Otavio Peixoto, custom OpenGL engine, 5 cascades, SDF raymarch per cascade, published 2024-12-18 (https://otaviopeixoto1.github.io/portfolio/2DRadianceCascades).
  - Godot: "basic port of Radiance Cascades shadertoy implementation" by Sohojoe (https://relatedrepos.com/gh/Sohojoe/radiance-cascades-godot) **[DATE?, renderer?]**.
  - sambigos, "2D Global Illumination in Godot": a Windows demo, "not plug-and-play", reference only (https://sambigos.itch.io/2d-global-illumination-in-godot) **[DATE?]**.
  - three.js: CodyJasonBennett/three-rc (https://scour.ing/@hello/p/https://github.com/CodyJasonBennett/three-rc).
  - Bevy crate solis_2d (https://lib.rs/crates/solis_2d).
- Chalmers MSc thesis "Exploration and Optimization of Radiance Cascades for Real-Time Applications" (https://odr.chalmers.se/items/3ee9fb4e-1880-46c2-802a-a660e38dc9ee/full). Not read in depth.
- **GodotFest 2025 (2025-11-12):** Jaanus Jaggo (Perfoon), "Raytracing is simple for 2D games". It covers a new 2D ray-traced lighting system for the indoor spaceship areas of *Blastronaut*, and claims simple shaders "perform much better than their 3D counterparts" (https://app.media.ccc.de/v/godotfest2025-raytracing-is-simple-for-2d-games). No numbers in the abstract.

### Inferences
- In Godot Compatibility there are no compute shaders, but RC and JFA are fragment-only ping-pong passes, so they map to a SubViewport chain or a DrawableTexture2D + `texture_blit` chain (4.7). Godot's built-in 2D SDF (`texture_sdf`, from LightOccluder2D) could replace our own JFA, but it only knows about occluders.
- Pixel-art fit: run RC on a 1/4- or 1/8-res light buffer and upscale with nearest filtering plus palette quantise. This gives chunky, banded GI that suits the style and hides ringing. Speculative.

### Gaps
- No measured RC numbers on WebGL2 mobile or iGPU. Godot RC ports have unknown maintenance status and Compatibility support.

## Q3. Games 2025–2026 praised for 2D/pixel lighting: technique sources

### Takeaway
- Hard technique sources from 2025–26 shipped *top-down pixel* games are scarce. Most of the coverage is marketing. The best technical sources stay older (Animal Well 2022 blog, Sea of Stars, Eastward). New in-period items: Mina the Hollower shipped (2026-05-29) but no lighting tech found; a GDC 2026 sprite-world talk; GodotFest/GodotCon pixel-VFX talks.

### Cited findings
- **Animal Well** (released 2024; tech blog from 2022-07-20, PlayStation Blog, Billy Basso):
  - Layered compositing, with light sources defined in front layers that light the background. Normal maps are "drawn manually" (paraphrase: hand-painted with the art).
  - Raymarched SDF background geometry and reflections. A Navier–Stokes fluid sim for water/smoke, with colours thresholded to the pixel palette. Custom engine. "the PS5's GPU makes short work of it".
  - Source: https://blog.playstation.com/?p=367113. No light counts or resolutions.
- **Sea of Stars:** a 2026-07-03 foro3d article says sprite shadows change with sun/moon position, the game runs real-time dynamic lighting in Unity at "60 fps en consolas y PC", and sprites were made in ProMotion NG (https://foro3d.com/2026/julio/sea-of-stars-pixel-art-de-16-bits-con-iluminacion-dinamica-en-unity.html). It cites no primary sources, so it is low reliability.
- **Mina the Hollower** (Yacht Club Games): released 2026-05-29 (https://www.shacknews.com/article/149025/mina-the-hollower-release-date; https://gameinformer.com/2026/05/06/mina-the-hollower-finally-launches-later-this-month). No lighting-tech source found.
- **Never's End:** GDC 2026 talk "How We Draw a 3D Sprite World" by Ryan Juckett. Slides posted 2026-06-08 (7 MB PDF, 341 MB PPTX) (https://www.ryanjuckett.com/how-we-draw-a-3d-sprite-world-gdc2026/; session https://schedule.gdconf.com/session/how-we-draw-a-3d-sprite-world-the-stylized-art-of-nevers-end/914052). Content not read.
- **Michael Vicente pixel-PBR experiment** (80.lv, 2025-05-26): hand-painted normal maps, roughness/metalness on pixel art, hidden geometry for shadows, day→night, 8-direction sprites, Unity (https://80.lv/articles/exploring-next-gen-pixel-art-with-real-time-dynamic-lighting). Experimental, not a game.
- **Isometric 2D lighting research** (arXiv, 2026-05-17; Rodrigues & Clua): infers 3D-ish geometry of 2D objects for real-time lighting of procedural isometric terrain, using opacity maps to fix visibility errors (https://gamedev.net/news/3395-a-real-time-lighting-technique-for-procedurally-generated-2d-isometric-game/). No numbers in the news item.
- **Older useful contrast:** Nectarmancer (2023-10-10) uses pre-baked directional **edge maps** in 4 channels instead of normal maps. Detecting edges in the shader would cost "8 extra texture reads per pixel" (https://80.lv/articles/how-pixel-art-lighting-was-set-up-in-seamless-world-of-nectarmancer).

### Gaps
- Hollow Knight: Silksong (2025), Fields of Mistria, Eastward: Octopia and Hades II were not researched for lighting tech in this pass. No Animal Well lighting talk (GDC) found.

## Q4. Community assets (last ~18 months)

### Takeaway
- **godotshaders.com** has many small CC0/MIT 2D pieces. The useful new ones for us are pixelated god rays, a procedural torch/candle flame, 2D cloud-shadow overlays and the "normal-map-only" TileMapLayer trick. Older but key: KPas's SDF soft-shadow light shader (2023, MIT), which handles up to 100 lights and costs per light, not per lit item.
- **"Lit" 2D Lighting Engine** (MIT, free, Godot store, v1.1.7 2026-10-17) is a full replacement for Godot 2D lights, but it is **Forward+ only, so not usable for web**.

## Q5. Web graphics state (brief)

### Takeaway
- WebGPU now ships in all major browsers, but with platform holes (Linux, Firefox Android, Intel Macs). Godot web export is still WebGL2/Compatibility. An **experimental** third-party Godot WebGPU backend claims about 4× WebGL speed. For 2026 planning, assume WebGL2.

### Cited findings
- web.dev, 2025-11-25 (https://web.dev/blog/webgpu-supported-major-browsers):
  - Chrome/Edge: Windows, macOS and ChromeOS since 113; Android since Chrome 121 (Android 12+, Qualcomm/ARM GPUs).
  - Firefox 141: Windows. Firefox 145 added macOS Tahoe 26 on ARM.
  - Safari 26: macOS, iOS, iPadOS and visionOS 26.
  - Linux and Firefox Android are "in progress".
- GodotCon Boston 2026 (2026-07-21): David Walter, "Godot WebGPU". It is a `RenderingDeviceDriver` that runs Forward+/Mobile in browsers. Claims "~4x faster than WebGL pipeline" and "~70% native", and it can run Forward+ GI. Experimental (https://talks.godotengine.org/godotcon-boston-2026/talk/CT739D/; repo https://github.com/dwalter/godotwebgpu).
- Godot 4.5 web export gained WASM SIMD (https://godotengine.org/releases/4.5/).

### Inferences
- If the WebGPU backend matures, Forward+-only tools (Lit, compute-based GI) become web options. Not before 2027 at the earliest; speculative.

## Q6. Normal-map generation for pixel art (incl. AI)

### Takeaway
- Brightness/Sobel generators (NormalMap-Online, Laigter-style height-from-luminance) misread drawn shading: dark belts become trenches and highlights become bumps. Shape-inferring AI tools do better on silhouettes, but every comparison found is vendor-written. A 2025 Eurographics short paper skips normals entirely: a UNet makes **light maps** directly from sprite + light vector. Hand-painted normals (Animal Well, Vicente) remain the quality bar.

### Cited findings
- "Light the Sprite: Pixel Art Dynamic Light Map Generation", Ivan Nikolov, Eurographics 2025 Short Papers (DOI 10.2312/egs.20251032). A UNet with CIN layers takes an RGB sprite and a light vector and outputs point/directional light maps; depth comes from ZoeDepth. Claims real time and results close to depth/normal-derived maps. Code: https://github.com/IvanNik17/light-sprite (https://diglib.eg.org/handle/10.2312/egs20251032). **[EXPERIMENTAL/research]**
- Sprite-AI comparison, 2026-08-05, **vendor-written**: brightness tools turn "dark belts" into trenches and rim light into a raised lip, but are frame-consistent (no flicker). Their AI tool is capped at 256 px per frame (https://www.sprite-ai.art/blog/normal-map-generators-compared).
- PixelNormalGen: $3.99, Windows/Linux. Pixel-art edge lighting (outer/inner edges, adjustable), aimed at a Katana-Zero-like look "without the blurriness" (https://nullabydev.itch.io/pixelnormalgen) **[DATE?]**.
- Earlier survey: "Analysis and Compilation of Normal Map Generation Techniques for Pixel Art" (arXiv 2212.09692, 2022) (https://ar5iv.labs.arxiv.org/html/2212.09692).

### Inferences
- For top-down 16–32 px tiles, a pixel-art **edge/bevel normal** (PixelNormalGen/Laigter bevel style) or 4-direction hand-authored normals is cheaper and more readable than AI depth. Nectarmancer-style 4-channel edge maps are an even cheaper option.

## Summary of what is new and usable for Kingsfoil (inference)
1. **DrawableTexture2D (4.7)** for a low-res light/fog accumulation map with add/mul blit. Check Compatibility support first.
2. **Instance uniforms (4.4)** plus additive light sprites for many flickering torches in one batch on WebGL2. The official docs still recommend additive sprites as the faster path.
3. **Radiance cascades / Holographic RC** are the state of the art for 2D GI and run in WebGL, but cost several ms on desktop GPUs. Use only as a low-res showcase.
4. **CC0 shaders** (torch flame, pixel god rays, cloud shadows) as drop-ins; the KPas SDF soft shadow (MIT, ≤100 lights) as an alternative to LightOccluder2D shadows.
5. Avoid Forward+-only addons (Lit) for web builds.
